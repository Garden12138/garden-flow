# 掘金首发草稿

状态：草稿，已与 v0.0.1 实际案例核对；尚未对外发布。

## 从资料到稿件和封面：我为什么做 GardenFlow

做内容时，资料、AI 对话、稿件和图片经常分散在不同地方。重新打开一个选题，除了继续写，还得重新找到它的背景和来源。

GardenFlow 想解决这个具体问题：把内容创作需要的上下文和产物，组织在同一个本地优先的桌面工作空间里。

### 用项目本身做一次例子

我为首次体验准备了一份公开的 GardenFlow 资料，包含功能、下载方式、模型配置、隐私和许可边界，并保留原始来源链接。

教程从这份资料开始：添加到知识库，在 AI 创作中选择来源，提出三个介绍角度，由人选定后继续写作。最终稿需要人工核对，再确认实际保存。封面作为可选步骤，使用独立配置的图片服务生成。

我在 macOS arm64 上用隔离的 `userData` 和工作空间跑了 v0.0.1。真实流程开始前，把现有文本、图片等模型配置同步到权限为 `600` 的临时数据库，没有复制生产聊天、稿件、知识库或媒体数据，也没有在日志中输出凭据。

文本使用 OpenAI-compatible 的 `qwen3.8-max`。生成三个角度的界面耗时约 1 分 25 秒；我选了“从资料到一篇有来源的介绍稿”。初稿保存后，人工删除 QA 路径和草稿状态，统一“文本模型”称呼并压缩重复段落，没有加入输入资料以外的产品能力和数据。

图片使用 `qwen-image-2.0-pro-2026-06-22`。图片工具调用约 1 分 4 秒，完整 Agent 执行界面显示 2 分 24 秒，得到一张 1080×1440 的 3:4 PNG；结果流和媒体库都能回看。实测也暴露出 v0.0.1 的显示问题：稿件在封面选择器中可能显示“未命名”且没有自动绑定，实际产物写入后任务卡仍可能停在“运行中”。所以验收以稿件和媒体文件为准，而不是只看聊天回复或任务状态。

### 为什么采用这些设计

**工作空间保存在本机。** 素材、稿件、媒体和运行记录围绕空间组织，工作区与 SQLite 承担本地状态。外部模型请求仍会发送给用户选择的供应商，因此本地优先不等于全部离线。

**模型由用户配置。** 文本与多媒体能力按路由配置；项目不提供共享密钥、默认网关或模型余额。这样也意味着，首次使用要先填对协议、Endpoint 和模型；聊天可用不代表图片可用。

**产物要能检查。** 聊天回复“完成”不是终点，稿件应能重新打开，媒体应有真实文件，来源应能回看。需要人工核对的部分应当保留在流程里。

**扩展连接本机桌面端。** 浏览器采集通过 Native Messaging 进入应用。安装包已经包含扩展资源，用户通过应用准备后再在浏览器加载，无需构建源码。

实现上，界面使用 Electron、React 和 TypeScript，主进程负责数据库、AI runtime、工具与本地文件。MCP 和 Skills 已有实现，本轮优先补足其使用说明和验证范围。

### 当前边界

v0.0.1 提供 macOS arm64/x64、Windows x64 和 Linux x64 安装包，目前未进行 Apple 公证或 Windows 代码签名。平台存在下载包不代表每个操作系统上的完整流程都已经实测。

GardenFlow 使用非商业 Source-Available 许可证，并非 OSI 认可的开源许可证。商用需要事先授权。模型服务可能收费，生成内容也需要人工审查。

首轮想先找到愿意实际完成一次创作的人，收集模型配置、资料导入、稿件保存中遇到的具体问题，再决定后续改进顺序。
