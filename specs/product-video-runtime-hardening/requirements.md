# Requirements

## Context

`session_1789876827205` 证明持久化确认已经生效，但运行时仍存在三类问题：渲染层可能把可见的 `@商品` token 作为普通文本发送、代理在没有结构化商品引用和视觉素材的情况下仍可提交商品视频提案、后台心跳会写入用户正在等待确认的主会话。

## Requirements

1. 提交消息时必须以编辑器 DOM 中真实存在的商品 token 为准，原子生成 `assetReferences`，不能依赖可能滞后一帧的 React state。
2. `product_video_compose` 在任何工作流中都必须要求恰好一个由主进程验证的商品引用，且 `productId` 与商品版本必须一致。
3. 商品视频规划必须获得 `assetId` 与真实图片一一对应的视觉输入；当前选择模型不支持图片输入时应在创建提案前明确阻断，不得静默切换到 GardenFlow 官方源或其他 AI 源。
4. 视觉规划提示必须要求基于实际画面分配镜头，并排除优惠规则、活动说明、过期价格等不适合作为通用商品镜头的素材。
5. 绝对素材路径只在主进程读取和转换，不进入商品引用 JSON、消息元数据或渲染进程。
6. 后台心跳不得写入 GardenFlow 用户主会话或待确认会话；若配置为输出报告，应写入独立的后台心跳会话。
7. 既有待确认记录不自动执行、不自动取消，也不因本次升级产生工程或模型费用。
8. 当用户粘贴的文本包含当前资产目录中唯一完整匹配的 `@商品名` 时，编辑器必须在发送前将其转换为带商品 ID 的可见 token；同名或无法唯一解析时不得猜测，且检测到已知资产名仍为普通文本时必须阻止发送并提示重新选择。
9. 任意前台 `video_generate` 调用都必须要求用户在确认卡中主动点击确认；自动 `ProceedOnce`、模型声称用户已确认或等待超时均不得放行。用户未确认期间不得提交视频生成任务。
10. 通用视频确认卡必须使用与操作相符的按钮文案；取消后本轮不得立即重试同一视频生成调用。
11. 商品视频分镜前必须完成一次可验证的多模态预检：校验值只能存在于图片像素中，模型必须正确读回并逐个返回全部 `assetId` 的画面分析；校验失败时不得启动分镜代理。
12. 运行时必须记录不含 Base64 和绝对路径的视觉输入诊断（模型、图片数量、素材 ID、校验状态），并拒绝缺少验证证据、使用被判定为价格/促销/活动素材，或试图用命令行文件列表替代视觉理解的提案。
13. 商品图片视觉准备必须在正式意图路由确定为 `product-video-compose` 之后、QueryRuntime 首轮请求之前执行；不得依据外层同步默认意图跳过视觉准备。多商品请求应要求用户选择唯一主商品，不得进入缺图错误。
